The Postgres image is PostGIS specifically, not stock Postgres — the schema uses geography(Point,4326) columns for travel_listing.location and traveler_profile.home_location, which a plain Postgres image cannot create.

02Process startup

main.py is the single entrypoint. It mounts two independent workstreams onto one FastAPI app: the trip-planning orchestrator and the data/RAG track.

Why the import order matters

load_dotenv() runs at main.py:35, before any app.* import. pydantic-settings populates the Settings object but never writes to os.environ — and langchain_google_genai reads GOOGLE_API_KEY / GEMINI_API_KEY straight out of os.environ. Without that call first, the LLM fails at runtime even with a perfectly filled-in .env.

Configuration

app/config/settings.py holds one Settings class read by nearly every module. Every field defaults to "" or a safe value on purpose — importing the app on a fresh clone with no .env must never raise ValidationError, so CI and a teammate's first checkout both work. llm_model defaults to gemini-3.6-flash because 2.0-flash and 2.5-flash now 404 for newly issued keys.

03The request graph

app/core/orchestrator.py builds a LangGraph StateGraph and compiles it once at import time, so orchestrator is a module-level singleton rather than rebuilt per request.

app/core/state.py defines TripState — the single Pydantic object threaded through all nine nodes. Every node mutates it in place and appends its own name to completed_steps.

  • recommendations (state.py:56) has to be declared even though only one agent writes it — Pydantic rejects assignment to undeclared attributes, so state.recommendations = [...] would raise.
  • budget_notes is kept separate from final_response so the generic "here's your trip plan" summary can't silently clobber the LLM's budget explanation.

Agent contract

app/core/base_agent.py is an ABC forcing every agent to implement async execute(state) -> AgentResult. app/core/result.py defines that result (success, state, message, error).

Why nodes don't append result.message

Agents mutate state in place and self-report failures into state.errors. So _recommend_node and _plan_node deliberately discard result.message — appending it too would list every failure twice.

04API layer

app/api/trip.py — POST /trip-plan, the only user-facing endpoint of the planner.

request→resolve GPS/IP→load session→build TripState→run graph→save session→curated response

Request shape

  • The field is named message, not user_input, to match the published API contract — internally it becomes TripState.user_input, because renaming it there would ripple through every agent file.
  • client_gps is a nested ClientGPS model rather than a raw dict, so FastAPI returns a clean 422 on malformed input instead of crashing, and it renders correctly in the generated Swagger docs.
  • session_id is omitted on the first message, then passed back to continue modifying the same trip.
Why location resolves here, not in the graph

trip.py:69 calls resolve_start_location() before invoking the graph, because only this layer can see the real HTTP request — TripState carries no client_ip field by design. The location node downstream is a fallback for direct callers (tests, scripts) that never had an HTTP request to begin with.

Multi-turn continuity

trip.py:71–86 mints a UUID or reuses the client's, load_session() restores the previous turn's fields and sets is_followup=True. This turn's freshly-resolved user_id and GPS always overwrite carried-over values — a new position fix beats a stale one.

app/utils/session_store.py persists that to trip_sessions.json, keyed by session id. _CARRY_OVER_FIELDS is an explicit allowlist: user_input, errors, clarification_needed, completed_steps and final_response are per-turn and deliberately excluded. The file itself flags this as interim — it should move to the real chat_session tables, arguably owned by NestJS since it already needs chat history for the sidebar.

Response shape

TripPlanResponse exposes only a curated subset of TripState. The candidate_* lists never leave the server, and completed_steps is populated only when settings.debug is true — internal state is never dumped straight out to a client.

05Nine nodes, in order

Each node is a thin async wrapper in the orchestrator that delegates to a tool or agent module and records its name.

01

validate

app/utils/validators.py — validate_trip_state()

Rule-based sanity checks, not a completeness check. Catches values that are present but invalid: non-positive duration_days or budget, travelers < 1, and any date window where start_date > end_date. Missing fields are fine — slot-filling handles those. Any error routes straight to respond.

02

policy

app/utils/policy_guard.py — check_policy()

A substring blocklist over user_input, positioned here so that blocked requests cost nothing — it runs before any paid LLM call. Entries are whole phrases, never bare words: "gun" alone would block "gun museum", "ivory" would block "Ivory Coast", a real destination.

A stated trade-off, not a stub

The module's own docstring records that a substring blocklist is inherently bypassable by paraphrase, misspelling, or translation. It stops the obvious case, not a determined bad actor — accepted for this project's scope, with an LLM content classifier named as the production replacement.

03

slot_fill · LLM call 1

app/utils/slot_filling.py — fill_slots()

Gemini with .with_structured_output(_ExtractedSlots) at temperature=0, extracting destination, duration_days, budget, travelers, interests and origin_location.

The system prompt hammers on never guessing — it explicitly forbids defaulting travelers to 1 just because a trip is being discussed. A missing value is the correct output when the user said nothing about that field.

Two modes:

  • First turn — only fills fields that are still None.
  • Follow-up (is_followup=True) — extracted values overwrite, because "make it cheaper" must actually change state.budget rather than being ignored on the grounds that budget was already set. Defaulting, profile lookup and clarification are skipped entirely.

If GPS and IP both failed but the traveler said "I'm starting from Polonnaruwa", the origin is geocoded via geocode_tool.py and stored with source: "text". GPS always wins when present — it's more precise than geocoding a place name.

Then: destination-only requests default to duration_days = 1; db_tool.get_user_profile() backfills interests, travel style and budget; and if there is still no destination, clarification_needed is set and the graph jumps to respond. The whole body is wrapped in try/except — it appends to state.errors and never raises.

04

location

app/tools/location_tool.py — resolve_start_location()

Early-returns when the API layer already resolved it, which is the normal HTTP path. Priority: GPS from the client → IP geolocation → None, which appends the soft error location_unresolved:.

Why ip-api.com and not ipapi.co

ipapi.co's unkeyed free tier returned HTTP 429 during testing (~1,000 requests/day). ip-api.com needs no signup and allows 45 requests/minute. The recorded trade-offs: plain HTTP only on the free tier, and a per-minute cap that a burst of concurrent demo testers could still trip.

05

calendar

app/tools/calendar_tool.py — get_free_days(user_id, 30)

Runs only when state.user_id is set. Four steps:

  • Read stored credentials from the google_oauth_tokens table.
  • Refresh the OAuth token if expired, and re-save it.
  • service.freebusy().query() over the next 30 days, collecting every busy date.
  • Invert to free days, then _group_into_ranges() collapses them into contiguous {start_date, end_date} windows.
Why a DB hit that finds nothing returns None

At calendar_tool.py:91–96: if the database is reachable and returns no row, the function returns None instead of falling through to the local JSON file. Falling through could resurrect a token the user deliberately disconnected. The file store is a fallback for "no database", never for "the database said no".

The whole query is wrapped in a bare except: return [] — a calendar failure must never block the graph.

06

context

geocode_tool.py · weather_tool.py · disaster_tool.py

First, geocode_tool.py resolves the destination through Nominatim (free, keyless), with the query biased by appending ", Sri Lanka". On any failure it returns None and the node degrades rather than guessing coordinates.

Dates come from the calendar windows if present, otherwise today + duration_days. Weather and disaster then run concurrently under asyncio.gather().

Weather

OpenWeather current conditions plus the 5-day/3-hour forecast, reduced per day to min/max temperature, the modal condition, and peak precipitation probability. Cached 45 minutes.

A timezone bug avoided on purpose

weather_tool.py:68–71 groups forecast slices by dt_txt — the UTC date string OpenWeather already provides — instead of fromtimestamp(), which applies the server's local timezone and would silently shift or drop forecast days depending on where the service is deployed.

Disaster

Three sources fan out concurrently: NASA EONET, USGS earthquakes (M ≥ 4 in the last seven days), and the GDACS RSS feed. Each filters by haversine distance within 300 km and maps its categories onto a red / orange / green severity rank. Cached one hour.

Failure and emptiness are different answers

Each fetcher returns None on failure but [] on a confirmed-empty result. Only when all three fail does the tool emit note: "disaster data unavailable" — otherwise a total outage would be reported as a confident, and possibly wrong, "safe".

Both tools sit on app/utils/cache.py, a thin async Redis wrapper that fails open: with no Redis, every call is a cache miss, never an exception.

07

recommend · LLM call 2

app/workflows/recommendation_agent.py

The heart of the system. It does recommendation and planning in a single call — merged deliberately to cut three LLM calls per request down to two, on the grounds that planning needs no data recommendation hasn't already gathered.

db_tool→index into RAG→retrieve top-6→build payload→gemini→parse→state
  1. Fetch candidate hotels, restaurants, attractions and events from db_tool; bail with an error if all three listing categories are empty.
  2. Index that pool into the RAG store under four categories.
  3. Build a query from interests + travel_style, falling back to the destination name, and retrieve the top 6 per category — _retrieve_or_fallback() reverts to the unfiltered list if retrieval scores nothing.
  4. Assemble the payload: candidates, weather_forecast, disaster_warnings, and traveler_request.
  5. On a follow-up, attach previous_itinerary and modification_request so the model refines rather than rebuilds.
  6. Parse, then write hotels, restaurants, attractions, events, the flat category-tagged recommendations list, itinerary, estimated_cost and budget_notes.
Why the raw message is sent every time

recommendation_agent.py:108 passes traveler_request — the user's verbatim words — alongside the structured fields. Slot-filling can't capture "vegetarian only", "no hiking, my knees are bad", or a preference for a relaxed pace, because none of those map to a tag. The prompt instructs the model to read it and account for it in each item's reason.

_parse_json_response() strips markdown code fences and returns {} on a parse failure — so every .get(key, fallback) below it degrades to the pre-LLM candidate lists instead of returning nothing.

app/prompts/recommendation_planning_prompt.py carries three binding rules: never invent a place outside the candidate list; avoid outdoor-heavy activities on days with severe weather or active disaster warnings; and every itinerary item must copy lat/lon from the candidate it represents, so the client can plot the route as map pins.

08

plan

app/workflows/planning_agent.py · app/prompts/planning_prompt.py

Usually a no-op. The node early-returns when state.itinerary already exists, which it does on every normal run. PlanningAgent is kept as a standalone fallback and for a future "regenerate my itinerary" action that shouldn't re-run recommendation.

09

respond

app/core/orchestrator.py:140

clarification_needed wins outright — if the graph needs to ask a question, that question is the whole response.

Otherwise errors are split into hard and soft using _SOFT_ERROR_PREFIXES = ("location_unresolved",). Soft errors are appended as a trailing "Note:" rather than being allowed to hide a perfectly good itinerary behind a failure message. A hard error only takes over the response when there's no itinerary to show.

06Data layer

app/tools/db_tool.py — every read is database-first with a mock fallback, so the service runs standalone.

Why raw SQL and not an ORM

Prisma, in the planned NestJS backend, owns the schema. Defining models here as well would duplicate that definition in a second language and let the two drift silently. So this module holds parameterised SQL strings instead.

  • _SELECT_LISTINGS is one JOIN across travel_listing, district and category, selecting latitude and longitude directly. Those are generated columns derived from the PostGIS location geography — which is why this file no longer decodes EWKB hex by hand, and why fetching listings is one round trip instead of three.
  • _coerce_date() exists because the columns are timestamptz and asyncpg refuses to coerce ISO strings the way the old Supabase REST layer did. Callers keep passing plain strings.
  • Mock dictionaries cover Ella, Kandy, Colombo and Galle. _get_mock_data() backfills lat/lon from district centroids so mock and real rows share exactly one shape.
  • get_user_profile() reads traveler_profile, using ST_Y/ST_X for home coordinates — consumed by slot-filling's defaulting logic.

Connection pooling

app/utils/db_pool.py holds one lazily-created asyncpg pool per process for the async request path. It returns None when the database is unconfigured or unreachable.

Why failure isn't latched

The pool deliberately retries rather than permanently pinning the service to mock data after one bad connect — a transient outage shouldn't degrade the service for the rest of its life. A 5-second connect timeout bounds the retry cost. It also logs at debug for "not configured" but warning for "configured but unreachable", so the two situations don't look identical in the logs.

Shared geography

app/data/sri_lanka_districts.py is the canonical list of all 25 districts: name (the human-facing key), osm_name (matching OSM's admin_level=5 area name), province, and an approximate centroid. Every pipeline reads this one list rather than hardcoding its own partial set, and assert len(DISTRICTS) == 25 guards edits.

07RAG subsystem

recommendation_agent→rag_service→retriever→vector_store→embeddings
ModuleRoleNotable decision
rag_service.py Module-level singleton facade Holds two things: a Retriever for per-category candidates, and a separate VectorStore("knowledge_docs") for guides and FAQs. Kept a plain sync class so async agents and sync scripts can both use it.
retriever.py One store per category _item_text() flattens name, description, tags, interests and destination into one searchable blob. build_metadata() stashes the original dict under "raw" so retrieval hands the agent back the full item, not just metadata.
vector_store.py FAISS, with a Python fallback IndexFlatIP over L2-normalised vectors, so inner product equals cosine. In-memory by design — the candidate pool is rebuilt per request, not persisted.
embeddings.py 384-dim vectors all-MiniLM-L6-v2, lazily loaded once per process, falling back to a deterministic MD5 feature-hash into 384 bins.
Two subtleties worth knowing

FAISS is skipped when a filter is active. At vector_store.py:112, the FAISS path runs only when filter_fn is None — FAISS can't apply a metadata predicate, so every destination-filtered search silently takes the pure-Python cosine path instead.

The hash fallback isn't semantic. It's stable and correctly normalised at the same dimension, so retrieval still runs without sentence-transformers installed — but the rankings it produces are not meaningful. It exists to keep the system importable, not to be a substitute.

08Batch ingestion

A second, entirely separate track: scheduled jobs that fill the database the request path reads from.

Scheduling

app/scheduler.py runs an APScheduler AsyncIOScheduler on Asia/Colombo, started from main.py.

JobCadenceSource
EventsWeekly · Mon 02:00Ticketmaster Discovery
Listings + pricesMonthly · 1st, 03:00OSM Overpass + Booking.com
WeatherNo jobFetched live per request, Redis TTL

_run_safely() wraps each job so one failed run logs an exception instead of killing the scheduler. The documented trade-off of running in-process: jobs only fire while the server is up, so a restart at the exact scheduled minute skips that run — the next week's or month's run still happens on schedule.

Listings — app/data/overpass_ingest.py

  • Per district, an Overpass QL query for tourism=hotel, amenity=restaurant, tourism=attraction and historic. 180-second server timeout, 200-second client timeout, one retry after a 15-second sleep on HTTP 429, and a 10-second pause between districts.
  • A second query pulls bus, rail and transit stations. Each listing is haversine-matched to the nearest stop within 1 km, setting has_public_transit and nearest_transit_stop.
  • Booking.com via RapidAPI adds real nightly prices — one destination lookup and one hotel search per district, not one call per hotel, which is what keeps it inside the free tier. It prefers the Sri Lanka match with the most hotels, because searchDestination returns same-named places worldwide. Matches are made within 1 km and bucketed into $ / $$ / $$$ / $$$$.
  • has_column("travel_listing", "price_per_night") gates the exact-price columns, so the job works both before and after that migration lands.
  • Rows whose district or category can't be resolved are dropped and logged rather than inserted broken.

Events — app/data/events_ingest.py

Ticketmaster Discovery, 50 km radius, 30-day lookahead, per district.

Recorded in the module docstring

Eventbrite was dropped as a source. Its public event search endpoint was deprecated in 2019 — third-party apps can now only list events for their own organisation, so it structurally cannot serve this use case, and /events/search/ returns 404 regardless of key validity.

Ticketmaster's key works but currently returns zero events for Sri Lanka (checked at Colombo, Kandy and Galle at 100 km). The job is kept running in case that changes, but real event coverage is expected to come from admin-entered events instead.

Writing — app/data/postgres_writer.py

The shared synchronous psycopg2 writer. Sync rather than asyncpg because these jobs run outside the FastAPI event loop, triggered by APScheduler or by hand.

  • get_district_id_map() / get_category_id_map() — name to foreign key.
  • to_point_wkt(lat, lon) → "POINT(lon lat)" — note the reversed order WKT requires.
  • has_column() — a cached information_schema probe.
  • upsert_rows(..., geo_columns={"location"}) — wraps geography columns in ST_GeogFromText(%s). Postgres will not implicitly cast a string into a geography column, so omitting a column from geo_columns fails the whole insert.

Every function no-ops cleanly when DATABASE_URL is blank, so ingestion can be run and tested without a database at all.

09Google OAuth flow

app/api/google_oauth.py — a two-endpoint side flow whose only consumer is the calendar node.

GET /auth/google/login→sign user_id into state→Google consent→GET /callback→verify state→save_credentials
  • Login signs the user_id into the OAuth state parameter with itsdangerous (URLSafeTimedSerializer, salt oauth-state), then redirects to Google with access_type="offline" and prompt="consent" — both required to actually receive a refresh token rather than just a short-lived access token.
  • Callback calls loads(state, max_age=600). A tampered or more-than-ten-minutes-old state raises BadSignature or SignatureExpired and returns HTTP 400.
  • It then exchanges the code and hands the credentials to calendar_tool.save_credentials(), which upserts into google_oauth_tokens — or writes the local JSON file when there's no database.
What the signed state actually prevents

Without it, anyone could call the callback with their own authorisation code and an arbitrary user_id, binding their Google Calendar to someone else's account. The signature makes the user_id unforgeable, and the 10-minute window bounds replay.

The google_oauth_tokens table is the AI backend's alone to write — the planned NestJS service does not touch it.

11The fail-open contract

The single design rule that runs through every module: no external dependency is allowed to raise. Each one has a defined degraded state.

DependencyDegraded behaviour
PostgreSQL (async)get_pool() → None, so db_tool serves mock data
PostgreSQL (sync)get_connection() → None; ingestion still runs, persists nothing
RedisCache miss on every call
Google CalendarEmpty list of free days
OpenWeatherNone — the planner proceeds without weather
All three disaster sources{safe: true, note: "unavailable"}
NominatimNone — the context node skips enrichment
ip-api.comNone → the soft location_unresolved error
Booking.comNo price enrichment; base listings still sync
sentence-transformersDeterministic hash embeddings, same dimension
FAISSPure-Python cosine similarity
LLM call or JSON parse{} → falls back to the pre-LLM candidate lists
Token store (database)Local JSON file — but only when the DB is absent, never when it says no

That contract is what makes the service runnable from a fresh clone with an empty .env, and what keeps the 19 test files in ai-backend/tests/ free of network calls.

12Two things to fix

Both surfaced while tracing the paths above.

Hardcoded event window

recommendation_agent.py:53 calls db_tool.get_events(destination, "2026-08-20", "2026-08-23") — dates left over from the mock phase, marked as such in the comment beside them.

It ignores state.trip_dates entirely, so once real event data lands, every request fetches events for the wrong four days. The fix is to derive the window from trip_dates, falling back to today + duration_days — the same defaulting _context_node already does for weather.

budget_notes lost on the fallback path

planning_agent.py:64 writes the LLM's budget explanation into state.final_response, which _respond_node then unconditionally overwrites with its own summary.

RecommendationAgent handles this correctly by writing state.budget_notes, which _respond_node appends. The PlanningAgent fallback should do the same — as written, a "no combination fits this budget" warning silently disappears on exactly the path where it's most likely to matter.
